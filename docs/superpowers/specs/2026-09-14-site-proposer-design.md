## Prospector — offsets in, keys out

> The model is only ever allowed to point at character spans in our own text; identity is decided by keys computed in Postgres (the same expression that built unified_sites.name_normalized) plus Wikidata/Wikipedia hard IDs, and every fuzzy signal may only ever produce a "possible duplicate of X" card the owner clicks — never a silent skip and never a silent "new".

## Pipeline

### 0. Key foundation — SQL match key, functional indexes, external-ID table

Three things, all zero-LLM, all measured.
(a) THE KEY. unified_sites.name_normalized is NOT normalize_name() output — orchestrator.py:1619 maintains it as `left(lower(unaccent(name)),500)`. Verified divergence on the curated set: 66 rows contain ı/ø/ş/ħ which Postgres unaccent folds ('Ayşepınar'→'aysepinar') but Python NFKD does not (normalize_name gives 'aysepınar'), and 46 rows keep parentheses ('Kemune (Zahiku)') which normalize_name strips. So ~110 of the 5,004 curated sites are unreachable by any Python-side exact match today — concentrated in exactly the Turkish corpus our content is heaviest in. The prospector therefore NEVER computes the match key in Python: candidate names go into SQL as raw bind params and the key is computed there, `left(lower(unaccent(:raw)),500)`, byte-identical by construction.
(b) THE INDEXES. `_find_site_by_name` runs `replace(name_normalized,' ','')` with no functional index. Measured on prod: `EXPLAIN (ANALYZE,BUFFERS)` on `WHERE replace(name_normalized,' ','')='derinkuyu'` gives a Parallel Seq Scan, 587,128 rows removed per worker, 21,564 buffer reads, 124.9 ms per lookup. Two functional btree indexes fix it — and fix the radar's existing hot path for free.
(c) site_external_ids. 4,632 of the 5,004 curated rows have `source_url LIKE 'https://en.wikipedia.org/wiki/%'` (measured; 0 have a wikidata.org URL). urldecode + underscore→space gives an enwiki title. All 4,632 then go through the SAME redirect-following batch API the candidates use — this is what makes the key SYMMETRIC (a curated row stored as /wiki/Sudama_Cave and a candidate named 'Barabar Caves' both land on 'Barabar Caves'). Verified live against the real API: `action=query&redirects=1&prop=coordinates|pageprops&ppprop=wikibase_item` returned redirects Sudama Cave→Barabar Caves and Smithsonian→Smithsonian Institution, with Q1311736 / Q131626 / coordinates in one response. 4,632/50 = 93 calls.

- **Ort:** migrations/0015_site_proposals.sql + scripts/backfill_site_external_ids.py + pipeline/lyra/prospector/keys.py::site_key_sql() (returns the one SQL fragment every other stage embeds, so the expression exists exactly once in the codebase)
- **Nutzt bestehendes:** pipeline.utils.http.fetch_with_retry, pipeline.database.get_session. Writes ONLY to site_external_ids — never to unified_site_names (the table caption_garble poisoned).
- **LLM:** none

### 1a. Paper mention extraction — the model returns offsets, never text

MEASURED CORPUS: 28 research_requests rows have result_json; only 25 have a `published_report` key (all 28 have `report`; the 3 without published_report are the non-public ones and are skipped with a logged count). 25 public papers = 1,054,372 chars. Cutting at `## References` leaves 908,818 chars; markdown figure markup `![alt](/data/research-images/…)` is another ~54,378 chars (358 images, ZERO <figure> tags — verified, so the api.services.theo_blocks splitter is not needed). Argument body ≈ 855k chars, avg 34k/paper, max paper 63,457.
Both regions are MASKED WITH SPACES, not deleted, so every char offset still indexes the stored report verbatim. Figure alt text is where the museum noise lives ('Part of Dead Sea Scroll 28a from Qumran Cave 1. The Jordan Museum, Amman' — a real sample) and masking means the model never sees it. The reference region is separately regex-harvested for en.wikipedia.org/wiki/ URLs — free hard keys, zero tokens.
The masked body is chunked into ~8,000-char windows on paragraph boundaries, each carrying its absolute offset. One M3 call per window. STRICT SCHEMA, no text fields at all: `[{name, place_class, char_start, char_end, country_in_text_start, country_in_text_end, period_phrase_start, period_phrase_end}]`, offsets relative to the window.
CODE-LEVEL GROUNDING ASSERTION applied to EVERY field the model emits, not just the name: the code converts to absolute offsets, re-reads `result_json::jsonb->>'published_report'` from the DB, slices, and requires `normalize_name(slice) == normalize_name(name)`. Mismatch drops the mention and increments `evidence_rejected`. country and period are slices too, so a hallucinated country is structurally impossible — that is the gap that sank the 'extraction' design, where only name and evidence_sentence were guarded while country/period/location rode through into unified_sites unchecked. A run whose reject rate exceeds 15% aborts rather than shipping degraded cards.

- **Ort:** pipeline/lyra/prospector/extract_papers.py + pipeline/lyra/prompts/prospector_mentions.txt
- **Nutzt bestehendes:** pipeline.lyra.minimax_shared.structured_llm_call (one keyword-only `thinking` param ADDED to it and forwarded to call_api — a 2-line change to the shared helper, not a copy), pipeline.lyra.theo_citations._find_references_heading, pipeline.lyra.text_sentences.sentence_span, pipeline.utils.text.clean_llm_name + normalize_name, pipeline.lyra.research_graph.is_junk_label, pipeline.lyra.site_matcher._GENERIC_NAME_BLOCKLIST (exported as GENERIC_NAME_BLOCKLIST, imported not copied)
- **LLM:** MiniMax M3 with EXPLICIT `thinking={'type':'disabled'}`. Not optional, and not what memory says: config.py:293 `thinking_for_effort()` returns `{'type':'adaptive'}` for EVERY effort level — its own docstring states 'effort no longer gates thinking on/off' and that disabled 'is never produced from an effort level'. `_call_anthropic_api` (config.py:405 pops it, :428 only defaults when None, :433 skips the adaptive max_tokens floor) preserves an explicit block. 855k / 8,000 = 107 calls, ~2,000 body + ~900 cached system in, ~700 out.

### 1b. Story mention extraction — the durable pump

This is the ONLY corpus with ongoing supply, and the numbers decide the design. MEASURED: news_items runs 62–172/week (last 8 weeks: 30, 108, 84, 172, 62, 103, 79, 88 — mean ~90). research_requests published 2 in May, 20 in July, 3 in August, ZERO since. Papers are a one-shot backlog; stories are the pump. Any design that sells papers as the steady state is selling a one-shot mining operation as an autonomous system.
Corpus unit = one news_item, deterministically reconstructed as `headline + '\n' + summary + '\n' + '\n'.join(facts)` (avg 1,411 chars; 5,024,671 total across 3,561 items). Six items per call (~8,500 chars), same offsets-only schema, same code-level slice assertion, offsets stored against the same deterministic reconstruction so they stay valid forever.
WHY NOT `news_items.entities` as the steady state: I measured it and it is a DEAD COLUMN — populated only between 2026-03-05 and 2026-04-12 (1,568 of 3,561 rows), and the only reference anywhere in the pipeline is the DDL `ALTER TABLE news_items ADD COLUMN IF NOT EXISTS entities JSONB` at orchestrator.py:592. summarizer.py never writes it. It is still worth mining ONCE (2,101 distinct names vs 1,006 in site_name_extracted), so it runs as a zero-token vein in 1d — but it is explicitly not what the weekly job reads.

- **Ort:** pipeline/lyra/prospector/extract_stories.py (shares the window/assert machinery with extract_papers via pipeline/lyra/prospector/mentions.py)
- **Nutzt bestehendes:** same set as 1a; plus news_items.timestamp_seconds + video_id for the evidence locator
- **LLM:** M3, thinking disabled. Steady state: 90 items/week = 15 calls. Backfill of all 3,561 items: 591 calls, tranched at 150/day.

### 1c. Absorb the existing radar backlog — zero LLM, this is what keeps the queue ONE queue

The 421 user_contributions rows with source='lyra' and enrichment_status='enriched' enter as candidates with `contribution_id` set. They are not re-proposed; their EXISTING card gains the dedup verdict and external match it cannot show today. Measured by the SQL key: of the 421, exactly 1 exact-matches an ancient_nerds name and 171 exact-match an external source — the trigram and levenshtein nets will raise both. This is the honest answer to 'the owner ends up with more review surface': the prospector adjudicates the backlog rather than sitting beside it, and GET /api/proposals serves one ranked list in which a radar card and a paper-derived candidate are the same object.

### 2. Resolve to a real-world entity — and NEVER launder a search hit into a fact

Batch 50 names/call to `en.wikipedia.org/w/api.php?action=query&redirects=1&prop=coordinates|pageprops&ppprop=wikibase_item|disambiguation`. Verified live: returns redirect target, QID, lat/lon and the disambiguation flag in one request.
THE FIX THE 'dedup' DESIGN MISSED: `site_identifier._pick_wikidata_entity` (line 1127) returns a QID with NO name check whatsoever when exactly one candidate has an enwiki sitelink — and that is the majority path, because direct title lookup misses often ('Phimeanakas Temple' → missing, verified). That is how a paper saying 'Sicyonian Treasury' ships a card with a real QID, real coordinates, a real Wikipedia article and a genuine verbatim sentence from our own paper — all four impeccable, describing Siphnian Treasury. So: after ANY resolution path the code requires `_is_same_name(candidate_name, resolved_label_en)`. Verified in Python against the real function: `_is_same_name('Sicyonian Treasury','Siphnian Treasury')` is False, `_is_same_name('Derinkuyu','Derinkuyu Underground City')` is True. On failure the entity is NOT attached; the candidate proceeds unresolved with `resolution_note` naming the rejected label. The QID is verified text-to-text exactly the way the quote is.
REJECTION FILTERS, each from a field the API actually returns: no P625 → `not_a_place` (kills 'Smithsonian Institution' — verified, no coordinates); P625 `precision` ≥ 0.1° → `area_not_point` (verified live: Texas precision=1, Great Zimbabwe precision=0.001 — the precision field IS in the raw claims, `_enrich_from_wikidata` line 1253 simply discards it, so that function gains two returned keys, `coord_precision` and `label_en`, which it already has in hand); P31 in the administrative/geographic-region denylist → `region`; `passes_date_cutoff({period_start, period_end, lon})` False → `out_of_scope` (the project scope function: Americas ≤ 1500 AD, rest of world ≤ 500 AD — it is what kills 'Cologne Cathedral', a real hit in the story vein).

### 3. Dedup ladder — set-based SQL over the whole batch, zero LLM

Four rungs; exact table in dedup_design. Written as ~6 set-based SQL statements that join the entire candidate batch against unified_sites in one pass each (the VALUES + LATERAL pattern that already exists in radar.py::_find_nearest_an_sites_batch), not as N per-candidate calls — at the measured 125 ms seq scan and 61 ms trigram probe, per-candidate calls over ~2,500 candidates would be 8+ minutes of saturating scans on the single Postgres that also serves the live API. `_find_site_by_name` is still imported and called on the single-candidate path at approve time so the two agree; the batch SQL is a different operation (n-vs-table adjudication), not a duplicate of it.

- **Ort:** pipeline/lyra/prospector/dedup.py
- **Nutzt bestehendes:** pipeline.lyra.site_matcher._is_same_name, _find_site_by_name, GENERIC_NAME_BLOCKLIST. It explicitly SUPERSEDES rather than silently reimplements two existing helpers, and says so: api.routes.radar._find_nearest_an_sites_batch (whose VALUES+LATERAL shape is the template) and pipeline.lyra.site_identifier._check_spatial_an_match (2 km + word_similarity 0.3 with a bare `except: return None`).
- **LLM:** none — an LLM is never asked 'are these the same site?'. That question produced Great Zimbabwe → Great Ziggurat of Ur.

### 4. Write proposals + evidence

Upserts site_proposals keyed on the partial-unique wikidata_qid / enwiki_title indexes, so a site named in a paper AND three stories is ONE proposal with four evidence rows. `evidence_count` is DERIVED with `SELECT count(*)` on every upsert, never `+= 1` — that is exactly how mention_count reached 34,061 against 2,464 real items. Ranks by (has external coordinates DESC, distinct corpus kinds DESC, evidence_count DESC) — explicitly NOT by mention frequency, because the frequency head of the unmined corpus is 'giza plateau' (85), 'göbekli tepe' (77), 'great pyramid' (46), 'egypt' (34), 'turkey' (20): frequency is an anti-signal for finding sites we lack.

## Dedup-Entscheidungstabelle

THE KEY, FIRST. Every comparison against the curated set uses `K(x) = left(lower(unaccent(x)),500)` computed IN POSTGRES on both sides. Never normalize_name(). Verified: Postgres unaccent folds ş→s, ı→i, ø→o, ħ→h; Python NFKD folds none of those four, so normalize_name('Ayşepınar')='aysepınar' while the DB holds 'aysepinar'. 66 curated rows have such letters and 46 keep parentheses in name_normalized — ~110 sites (2%) that a Python key can never hit, concentrated in the Turkish corpus. This is the most consequential correction to what I inherited: all three source designs called normalize_name "the identical function unified_sites.name_normalized was built with", and it is not.

=== THE DECISION TABLE ===

R0 — HARD IDENTIFIER. Verdict `have_it` (auto-skip).
  R0a candidate.wikidata_qid ∈ site_external_ids(kind='wikidata_qid') on an ancient_nerds row.
  R0b candidate.enwiki_title (AFTER redirect resolution) ∈ site_external_ids(kind='enwiki_title').
  Both sides went through the same redirect batch, so the key is symmetric — a curated row stored as /wiki/Sudama_Cave and a candidate named 'Barabar Caves' both key to 'Barabar Caves' (verified live). Single btree lookup on (kind,value); no scan of the 1.76M table. Coverage 4,632/5,004 = 92.6% by title today.
  DOWNGRADE 1 (redirect collapse): decisive only if `_is_same_name(candidate.name, matched.name)` OR `_is_same_name(candidate.enwiki_title, matched.name)`. A redirect can collapse a genuinely distinct child onto its parent; prod holds 1,748 ordered pairs of curated sites within 100 m of each other, so parent/child coexistence in our own data is the norm. Failure → R2 `needs_decision` showing the redirect chain.
  DOWNGRADE 2 (key collision): if R0 returns 2+ curated sites (115 enwiki-title collisions exist), it is NOT decisive → `needs_decision` listing every collided site. A key that points at two things is not a key.

R1 — EXACT NAME ON THE CURATED SET. Verdict `have_it`.
  K(candidate.name) = us.name_normalized, or = usn.name_normalized, or spaceless-equal on either (the two new functional indexes), with source_id='ancient_nerds'.
  GUARD: if both sides have a country and they disagree after normalize_country + country_name_variants, downgrade to `needs_decision`. 750 of the 5,004 curated names have a same-named site in a different country elsewhere in unified_sites, so ungated exact-name equality is a silent-suppression channel pointing the opposite way from the Great Zimbabwe incident.

R2 — RECALL NETS + GATES. Verdict `have_it` only under the triple condition below; otherwise `needs_decision`.
  Nets (each ONE batched SQL statement over the whole candidate set, VALUES + LATERAL, DISTINCT ON (candidate, site)):
    N1 `:name <% usn.name_normalized::text` at word_similarity_threshold 0.5. VERIFIED on prod that this uses idx_usn_name_trgm (EXPLAIN shows Bitmap Index Scan, 61 ms), and I ran the actual batch against the curated set. Real output: derinkuyu→'Derinkuyu Underground City' 1.000; osirion→'Osirion' 1.000; great zimbabwe→'Great Ziggurat of Ur' 0.533; lake van→'Glastonbury Lake Village' 0.667 and 'Meare Lake Village' 0.667; meadowcroft rockshelter→'Tham Lod Rockshelter' 0.500; espiritu pampa / bubastis / humeima → nothing.

## Nachvollziehbarkeit

THE MECHANISM: the model returns character offsets and the code returns the text. The extraction schema has NO text fields at all — `[{name, place_class, char_start, char_end, country_in_text_start, country_in_text_end, period_phrase_start, period_phrase_end}]`. propose.py re-reads the source from the DB, slices, and asserts. A model physically cannot fabricate a quote, a country or a period through this path, because it never supplies one. Crucially this is applied to EVERY model-emitted field, not just the name — the field that carries the fact (country) gets the same guarantee as the field that carries the label. That is the gap the "extraction" design left open, where a hallucinated location phrase was printed as ground truth and drove globe centering.

ASSERTIONS, in code, after every response:
  1. `normalize_name(source[abs_start:abs_end]) == normalize_name(name)` — else drop the mention, `evidence_rejected += 1`.
  2. country_in_text and period_phrase slices must be non-empty and inside the same paragraph as the name — else those fields are set NULL (the mention survives; only the unverifiable claim dies).
  3. Run-level: `evidence_rejected / mentions > 0.15` → the run aborts before writing any proposal. That ratio is a direct drift alarm on the model or the prompt.

THE QUOTE: `pipeline/lyra/text_sentences.sentence_span(unit_text, char_start)` — chosen because it preserves offsets exactly by construction (its `_protect` swaps each protected period for a single sentinel char, so positions are unchanged) and it will not amputate a sentence at "Paul S. Martin".

WHAT THE OWNER SEES per proposal:
  • the name as written, the resolved Wikidata entity as a clickable QID + the Wikipedia article the coordinates came from, and — when resolution came from a search rather than a direct title hit — an explicit line: `resolved via search; label "X" accepted by same-name check`. A card never renders a guessed entity identically to a pinned one, which was the "dedup" design's second blind spot: on names like "Asan Kroy" or "Mataha Labyrinth" the owner has no prior and no way to notice a wrong QID.
  • N evidence rows, each a verbatim sentence with a locator that lands on it:
      paper → `/research/{slug}#:~:text={urlencode(quote[:40])}` (verified route at api/routes/research_html.py:127; research_requests has a `slug` column). `footnotes` captures the `[n]` markers in the quote's paragraph and the API resolves them against the paper's own numbered reference list, reusing the citation apparatus the citation-integrity gate already validates.
      story → `https://www.youtube.com/watch?v={video_id}&t={timestamp_seconds}s` from news_items.
      radar → the contribution's existing source_url.
  • `dedup_trace` as an expandable "what I checked" panel printing the literal arithmetic: `{"net":"N1_trgm","site":"Great Ziggurat of Ur","word_similarity":0.533,"killed_by":"G1","candidate_country":"Zimbabwe","site_country":"Iraq"}` and `{"net":"N1_trgm","site":"Tham Lod Rockshelter","word_similarity":0.500,"shared_tokens":["rockshelter"],"df":22,"g3":"pass","killed_by":"G1"}`. A card never says "new" without showing what it considered and why it declined.
  • `location_rung` printed literally: "coordinates from Wikidata P625 (precision 0.001°)" / "from geonames row X, 1.2 km from the Wikidata point" / "none — you place the pin". A rung='none' proposal cannot be approved, because `_missing_core_fields` refuses it.

NOT presented as provenance: place_class, site_type and the normalized period are model or ontology judgements about the name, not claims about a site. They are labelled "classification" and kept out of the evidence list.

Nothing is ever deleted. `have_it`, `out_of_scope` and `not_a_place` rows stay queryable, and `GET /api/proposals?status=have_it` exists precisely so the owner can audit the skip channel — the only channel that can lose a real discovery.

## Fehlermodi und ihre Wachen

- A search engine picks the wrong entity and the card ships a real QID, real coordinates, a real Wikipedia article and a genuine verbatim sentence from our own paper — all four impeccable, describing the wrong building. This is the failure that survives every other guard, because nothing about the card looks wrong. GUARD: `_is_same_name(candidate_name, resolved_label_en)` is required after EVERY resolution path, including the `_pick_wikidata_entity` single-sitelink short-circuit that returns a QID with no name check at all today (site_identifier.py:1127). Verified: it returns False for Sicyonian Treasury vs Siphnian Treasury. On failure the entity is not attached and `resolution_note` names the rejected label on the card.
- The extractor hallucinates a place name, a country or a period. GUARD: the model returns only offsets; the code slices from the DB and asserts every field, not just the name. `evidence_rejected/mentions > 0.15` aborts the run. No repair, no fuzzy acceptance, no caveated storage.
- A wrong auto-skip loses a real discovery forever and the owner never learns it existed. This is the only irreversible channel in the system, so it gets the strictest gate: auto-skip fires only on a hard identifier (same Wikidata entity or same Wikipedia article, both with a same-name confirmation) or on the triple condition (same-name AND country agreement AND ≤250 m). Everything the keys cannot settle becomes `needs_decision`, which costs one click and costs the data nothing. Skipped rows are never deleted and `GET /api/proposals?status=have_it` exists to audit them.
- A Wikipedia redirect collapses a genuinely distinct child site onto its parent article. Not hypothetical: 1,748 ordered pairs of curated sites sit within 100 m of each other, so parent/child coexistence is normal in our own data. GUARD: a rung-0 hit is decisive only when `_is_same_name` also holds; otherwise it is downgraded to `needs_decision` with both names and the redirect chain shown.
- A curated enwiki title collides — 115 such collisions exist among the 4,632 titles. GUARD: site_external_ids is deliberately NOT unique on (kind,value); rung 0 returns a set, and a set of size > 1 is not decisive. The card lists every collided site.
- Coordinates come from a Wikidata region centroid and the owner pins the middle of a province — 'Texas' resolves to (31,-99) WITH coordinates present, verified live, so a coords-required filter alone does not catch it. GUARD: three stacked filters — no P625 → reject; P625 `precision` ≥ 0.1° → reject (verified: Texas precision=1, Great Zimbabwe 0.001; `_enrich_from_wikidata` line 1253 currently discards this field and gains it as a returned key); P31 in the administrative-region denylist → reject. Plus `_missing_core_fields` still gates approve.
- An external homonym writes a false coordinate that rides through approve into unified_sites — 'Cydonia' the Mars feature matching coins_nomisma's Kydonia on Crete. GUARD: rung 3 contributes coordinates only when the external row passes the G1 country gate against the resolved Wikidata country OR sits within 50 km of the resolved P625 point; otherwise it is an annotation with no field copied.
- Medieval-European or off-Earth material leaks in. GUARD: `passes_date_cutoff({period_start, period_end, lon})` — imported, not reimplemented; it IS the project scope rule (Americas ≤ 1500 AD, rest of world ≤ 500 AD) and is what kills Cologne Cathedral, a real hit in the story vein. Plus `place_class='off_earth'` and a hard QID denylist for Mars/Moon features, which the paper corpus will produce (there is a Valles Marineris paper). Out-of-scope candidates get `status='out_of_scope'`, recorded not deleted, so the rule stays auditable.
- The same site is proposed twice from two corpora and the queue fills with near-identical cards. GUARD: partial unique indexes on wikidata_qid and enwiki_title collapse them into one proposal with two evidence rows; the fallback name-key unique is scoped by country so two real 'Glenwood' sites (osm_historic California, canmore_scotland Aberdeenshire — both real prod rows) do not collapse into one. `evidence_count` is derived with `SELECT count(*)`, never `+= 1`.
- The dedup pass saturates the production Postgres that also serves the live site. Measured risk: the spaceless lookup `_find_site_by_name` performs is a 125 ms parallel seq scan over 587k rows per worker, and the trigram probe is 61 ms. GUARD: two functional indexes in migration 0015 remove the seq scan entirely (and speed up the radar's existing path), and the whole ladder is ~6 set-based statements over the batch rather than 2 × 2,500 per-candidate calls.
- Wikipedia/Wikidata is rate-limited or down and the run writes garbage. GUARD, stated accurately rather than optimistically: `_enrich_from_wikidata` and `_check_enwiki_sitelinks` both catch broadly and return {} — they do NOT raise, so exception propagation is not the guard. The run counts `resolver_failures`, and if more than 20% of a batch fails to resolve it aborts BEFORE writing any proposals and leaves candidates unprocessed for the next cycle. Half-written state is the thing to avoid, not a failed run.
- A name the owner already judged comes back every week. GUARD, and deliberately NOT auto-rejection: 271 of the 273 not_a_site/rejected contributions are LLM verdicts (site_identifier.py:395 and :1828/:1845 — 'rejected' means an LLM refused a proposed MATCH, so the site is real and merely unmatched; prod carries 'Bat Creek Mound' rejected against 'Garden Creek site'). - The backfill dumps 600 cards and the owner reviews 20. GUARD: ranking by (has external coordinates, corpus diversity, evidence count) — a card with free coordinates and a site_type is two clicks from promoted, so the top of the queue is the part that costs the least. ### dedup
- Stage 4 calls pipeline.lyra.site_matcher.fill_contrib_from_site(contrib, site) on a site_proposals row, but that function (site_matcher.py:485) reads and writes contrib.wikidata_id and contrib.wikipedia_url. One of the three stacked guards against province-centroid pins therefore does not exist until that function is modified, which the design presents as pure reuse.
- Failure-mode #1 guarantees 'no try/except-return-empty anywhere in resolve.py -- fetch_with_retry raises and the stage raises', but resolve.py is built on _enrich_from_wikidata (try/except -> return {}) and _pick_wikidata_entity (except LyraAPIError -> return None).
